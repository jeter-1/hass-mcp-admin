# Engineering 2.2.0-beta.33 acceptance

This procedure applies only after independent review, merge, protected
promotion, publication, and separately authorized deployment. Source
validation must not access the deployed Home Assistant environment. Use fresh
plans; do not reuse the earlier prohibited garage plan or any consumed approval.

## Pre-deployment gates

1. Confirm source, generated add-on metadata, image labels, tag, and accepted
   commit all identify `2.2.0-beta.33`.
2. Confirm the complete unit suite, Full and Evidence gates, exact-image bake,
   exact add-on runtime acceptance, and both supported Home Assistant lanes
   pass.
3. Confirm the positive fixture retains the exact garage-close action and adds
   only an enabled top-level obstruction/safety condition. Require
   `elevated_admin`, `moderate` delta, `safety_critical` consequence, a complete
   condition-only semantic projection, and two ordered administrator actions.
4. Confirm create, changed action/service/target, broadened trigger, removed or
   replaced condition, blueprint, dynamic/unresolved structure, and unreviewed
   guard fixtures remain prohibited with no task or provider reachability.
5. Confirm stable v1.1.2, public schemas/catalog, ha-mcp 8.2.0 exact admission,
   provider routing, dashboard and notification behavior, and zero-fallback
   accounting are unchanged.

## Read-only smoke checks

1. Confirm `server_info`, image/build provenance, and health identify the exact
   accepted Beta 33 artifact.
2. Confirm governance storage, approval Ingress, F3 task/recovery health,
   providers, delegated reads, dashboard provider, notifications, and fallback
   counters are healthy and unchanged before creating a plan.
3. Read the exact current garage automation and identify the existing retained
   safety-critical effect. Keep unknowns explicit; do not reconstruct the
   current configuration from a prior plan or conversation.

## Fresh garage risk-reduction canary

1. Prepare one fresh full-config update that preserves the exact current
   action/control-flow graph, triggers, mode, and other behavioral fields and
   only appends the approved top-level safety guard. A metadata-only alias or
   description edit may accompany it, but is unnecessary.
2. Confirm planning reports `risk.level=high`,
   `policy_class=elevated_admin`, `risk_delta=moderate`,
   `physical_consequence=safety_critical`, and the four retained-effect reason
   codes documented in the release notes.
3. Review the complete semantic projection. Confirm it shows only the appended
   condition (and any deliberately requested metadata) and no action, target,
   trigger, mode, or unrelated delta.
4. Complete the exact-plan approval and elevated-risk acknowledgement through
   authenticated Ingress as the same Home Assistant administrator. Confirm MCP
   planning and approval-request tools grant no authority themselves.
5. Apply once. Require one durable F3 task, exactly one configuration-provider
   dispatch, provider response received, no fallback, exact readback match,
   valid configuration check, and terminal `succeeded_verified`.
6. Independently reread the automation. Confirm the exact guard is present and
   the retained action/control-flow graph is unchanged.
7. Repeat the same apply request only to prove idempotent `already_applied` and
   zero additional provider dispatches. Do not trigger the automation or move
   the garage door as part of acceptance.

## Negative and recovery acceptance

1. Prepare, but do not approve, a fresh proposal that changes the retained
   service or target. Confirm it is `prohibited`, creates no approval challenge
   or execution task, and cannot reach a provider.
2. Prove a separately prepared and approved positive plan fails pre-dispatch if
   authoritative current state changes before apply. Require zero provider
   attempts and a terminal `failed_pre_dispatch` task with truthful stale-state
   evidence.
3. Confirm restart/reconciliation never converts a missing, stale, or malformed
   retained-effect proof into approval or dispatch authority and never blindly
   redispatches a post-dispatch task.

## Acceptance result

Beta 33 passes only when the fresh garage risk-reduction plan completes through
both elevated approval actions and one verified dispatch, while every broadened
or ambiguous variant remains unreachable. Any changed physical effect admitted
by the exception, incomplete review projection, stale-state dispatch, duplicate
dispatch, fallback, or claim that the guard's live effectiveness was proven is
a blocker.
