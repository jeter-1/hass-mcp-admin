## 1. Source and offline acceptance

Bind:
- the Lows bundle contract (architect, 2026-11-05) and the architect's
  acceptance of the HAMCP-304 diagnosis below;
- the HAMCP-304 cause, at the 2.4.2-beta.3 base `468d0278`:
  - `governance/record_inspection.py:58` screened the stored
    `approval_kind` (`apply` or `rollback`) against `ApprovalActionKind`,
    which names approval action records. Every stored kind therefore showed
    `unrecognized_value`;
  - `governance/service.py:1693` and `:1722-1723` accepted only
    `change_plan_created` as a prohibited plan's creation event. Contract-v3
    operational plans record their own operation's event (`:4408`, `:4641`,
    `:5074`, `:5366`). So every never-approvable prohibited operational plan
    failed projection with `approval_sequence_inconsistent`;
- **the rejected hypothesis.** Loss of the kind on expiry was the working
  hypothesis. The shipped writer shows that expired plan `d3af624a` still
  stores `approval_kind: apply`, so the kind was never lost;
- the non-goals:
  - no change to approval, apply or dispatch rules;
  - no persisted-format change and no stored record rewritten;
  - no schema, provider or tool change;
- `2.4.2-beta.4` materialized before Ready, with exact document resolution;
- the PR head SHA, its `validate` run and the Evidence tier log named in the
  PR.

The review needs a security section covering:
- **No new reachability.** No new tool, route, provider dispatch, write or
  fallback.
  - Prohibited plans stay never approvable. `approve` now refuses them with
    `prohibited_change` instead of `approval_sequence_failure`.
  - `apply` is still refused, with zero dispatch and no execution task.
- **Exact event mapping.** The prohibited-shape check accepts exactly one
  creation event per plan:
  - the plan operation's own event, for contract-v3 operational
    administration plans;
  - otherwise, `change_plan_created`.

  Any other creation event still fails it, as does any extra event or
  execution evidence.
- **Acknowledgement fallback.** The 2.4.2-beta.3 view fingerprint is
  recomputed only when a stored acknowledgement mismatches, and only for
  plans. It is never stored and never shown. It matches only an unchanged
  record, and a new acknowledgement must bind the current fingerprint.

Required offline evidence:

  - **Fixtures.** Live-shaped fixtures for plans `2ab4764f`, `faba2fbd`,

    - health `projection_failure_count` 0;

    `rollback` is recognized, and other values still show the marker.
  - **Exact event mapping.** A table test over every operational
    operation:
    - only the operation's own event is accepted;
    - another operation's event, unrelated events, and `<op>_plan_created`
