# Engineering 2.2.0-beta.48 release notes

Beta 48 stages a target-scoping correction for helper dependency risk.
Engineering 2.2.0-beta.47 remains advertised until protected promotion. Stable
v1.1.2 and the 51-tool Engineering catalog are unchanged.

## Target relevance precedes consequence

Each obligation now persists a bounded selector-scope proof from the immutable
dependency-index snapshot. The helper projection resolves that proof against
the exact requested entity before selecting downstream profiles or aggregating
semantic completeness, physical consequence, policy, actionability,
fingerprints or locks.

Closed finite candidates, complete label membership and complete entity domains
can prove exact inclusion or exclusion. Reviewed trigger context identity and
duration values are dependency-neutral unless their resulting scalar is later
used as an entity selector. Unknown callables, dynamic selectors, incomplete
registries, overflow and processing failure remain target-capable or
coverage-failed. Diagnostic candidates on an unresolved obligation never become
an exclusion proof.

Consequences now attach only when an exact target edge, genuine target-capable
opacity or target-relevant coverage failure survives. An unrelated source's
unknown action effect no longer poisons a helper after every causal relationship
from that source has been excluded. Independent exact edges remain visible and
retain proportional consequences.

New plans use `helper-dependency-risk-v7`. Persisted v3-v6 plans stay readable
but require replanning and cannot authorize approval, lock projection or
dispatch. Risk, approval binding, final preflight, observability and F3 consume
the same target-scoped evidence.

## Compatibility and non-actions

No public MCP schema, tool registration, provider admission or routing,
fallback, helper write authority, approval authority, task schema, workflow,
container, deployment or stable-v1 surface changes. Existing durable intent,
one-attempt dispatch, authoritative reread, duplicate suppression,
readback-first recovery, audit and authenticated plan pagination remain
unchanged.

This staging task performs no merge, promotion, publication, deployment,
restart, live Home Assistant access or governed helper mutation. Post-deployment
read-only planning acceptance and any helper canary require separate authority.
