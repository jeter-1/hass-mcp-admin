# HAMCP-371 SB: write providers and the dashboard attestation on 9.2.0

SB binds the typed power, fan and helper-value providers and the F3 dashboard
provider to exact ha-mcp 9.2.0, and moves the 9.2.0 dashboard attestation from
`quarantined` to `reviewed`. It carries out:

- plan list B, authorized "as an upper bound", with each provider bound "only
  after its own v9.1.2 to v9.2.0 diff review";
- item 20: "a descriptor-only change is not "changed semantics". Rebind after
  reviewing the new description for behavioural claims";
- the Q8 ruling: "At SB, write the upstream_dashboard_builtin_attestations.json
  entry from the capture, set the attestation to "reviewed", and replace that
  test with a positive-path test asserting 9.2.0 dashboard admission."

The per-provider diff reviews are `docs/evidence/hamcp371/sw-write-providers.md`
(SW). This file is the receipt half of SW: which payloads, and where.

This is a local candidate only. Nothing was signed, published, pushed or
deployed, and no Home Assistant instance was accessed. No signing or workflow
step was used for the attestation.

## The attestation entry

Written by the local `scripts/review_upstream_read_release.py
dashboard-attestation` command from the S8 capture, then carried through the
S8 pipeline (`inputs`, `run_candidate.sh`, `finalize`, `contract-review
--check`). Entry `ha-mcp-v9.2.0-9de5bf6c`, source `v9.2.0` `51e3aac7…`,
image index `sha256:9de5bf6c…`, review evidence digest
`sha256:377d810c…` (the contract review), attestation fingerprint
`8d67aaf0…`, constraints fingerprint `b020f2f3…`.

Against the 9.1.2 entry:

- **Equal:** `contract_family` (`ha_mcp_dashboard_read_v3`), the input,
  output, raw input-schema, runtime and security contract fingerprints,
  `server_name`, `revoked` (false), the constraints fingerprint, and the three

  introduced here.

  image index and platform digests, image revision, catalog fingerprint,
  review evidence digest, `reviewed_at`, `upstream_version`.

The registry row's dispositions equal 9.1.2's: read gateway and dashboard
admitted, backup and lifecycle held. The Q8 S13 check ("the 9.2.0 registry row
and attestation equal 9.1.2's in disposition and attestation state") is still

## Disclosures

- **Strict endpoint form.** 9.2.0, like 9.1.0 and 9.1.2, is admitted only on
  the strict `/catalog/full` endpoint (`clients/ha_mcp_endpoint.py:38`
  `STRICT_FULL_SELECTOR_RELEASES`; check at `:454`). The shipped HAMCP-175
  peer asserts the legacy empty URL, so `Public920` reaches it through a
  synthetic, never-resolved `/catalog/full` URL. The legacy form on 9.2.0
  raises before `tools/list` (tested).
- **Synthetic peer shapes.** The `Public920` peer replies and the 9.2.0 getter
  peer in `test_hamcp371_dashboard_getter.py` are synthetic shapes from the
  shipped 9.1 harnesses, not cited from 9.2.0 source. They test admission and
  refusal, not the 9.2.0 reply shape; the reply shapes are covered by the P6
  receipts above and by SR.
- **Not observed:** no `ha_call_service` receipt and no
  `ha_config_set_dashboard` receipt on 9.2.0. Neither write was run against
  the disposable Core. P6 covers one helper domain (`input_boolean`); the
  fan and power domains' action keys and reply sizes on 9.2.0 are unobserved
  until SR or live acceptance.
- **`capabilities.py` public capability text.** No `capabilities.py` source
  line changed, but the power and fan capability `trust_profile` strings
  (`capabilities.py:1091`, `:1132`) join `POWER_CONTRACTS` and `FAN_CONTRACTS`,
  so each now also lists the 9.2.0 contract name
  (`core-2026.9.2-ha-mcp-9.2.0-single-power-v1`,
  `core-2026.9.2-ha-mcp-9.2.0-single-fan-v1`; 5 names to 6 on each, checked
  against `main` `e741f2ed`). This is a public capability-text change. The
  dashboard capability text is unchanged.
- **Stale text remains.** `build_candidate_inputs.py:492` still says
  "ha_get_history refuses before dispatch until S9". It refers to the S8
  interim history refusal, which S9 replaced with `upstream_history_9_2.py`
  (offset-qualified and relative times forwarded; others refused); it is
  a generator string in the regenerated review notes and was left as written
  in SB, because changing it changes regenerated output outside the SB scope.
  The dashboard part of that string says "reviewed (SB)". The committed S8
  receipts written before SB keep their original text.
- **`test_hamcp319_used_tool_exact_admission` fails on the branch** (ruling
  item, below).

## Ruling item: `test_hamcp319_used_tool_exact_admission`

The SB row that adds 9.2.0 to `EXACT_GETTER_RELEASES` makes one shipped test
fail: `Scope.test_exact_used_tool_releases` asserts
`EXACT_GETTER_RELEASES == frozenset(VERSIONS)`, and `VERSIONS` is
`('8.5.0', '9.1.0', '9.1.2')`. The module passes on `main` and before SB, and
HAMCP-351 edited it for 9.1.2 (`bcdff105`).

A version and file-list edit was tried in the worktree and reverted. It added
`'9.2.0'` to `NINE_ONE`, and `WIRE_920` pointing at the committed 9.2.0
standalone filesystem-on `tools/list` in wire order
(`s8/profiles-2/out/standalone-9.2.0-fs-on/observation.json`
`tools_list_pages[0].response.result.tools`; 82 descriptors, equal to that
profile's `capture.json`). The patch is `.artifacts/sb/ut/trial3.patch`, not
committed.

With that edit, the scope, read-gateway, YAML-reader and typed-control
classes pass on 9.2.0. The dashboard class fails: 37 errors, all
`KeyError: '9.2.0'` from `DashboardPeer` in `tests/test_hamcp319_dashboard.py`
(its `URLS` and `NINE_ONE` have no 9.2.0). Making it pass needs a 9.2.0 row
there. That module passes on the branch, so it is outside the T129 edit set,
and the row would assert that 9.2.0 dashboard replies have the synthetic 9.1
envelope shapes, which is a 9.1.2 value copied by analogy. The module is
therefore left unedited and fails on the branch, pending a ruling.

Ruled 2026-11-15 17:50 CST, (a): trial3 applied, and a 9.2.0 dashboard peer row
added with its sources cited. See `../s13/README.md`, "SB used-tool ruling".
