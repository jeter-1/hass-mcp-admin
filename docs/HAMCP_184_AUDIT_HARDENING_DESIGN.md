## 2. F-05 — provider dispositions fail closed

**Defect.** `ReviewedUpstreamRelease.provider_disposition` returned
`dict(...).get(surface, "admitted")`. An entry, or a surface, with no declared
disposition was admitted by omission. Five compiled entries had no
dispositions.

**Change.**

1. The accessor returns the declared value only when it is one of
   `admitted`/`partial`/`held`. Otherwise it returns `held`.
2. `provider_dispositions` moved from optional to required in the entry field
   check. The loader now validates it unconditionally, so it must be an object
   with exactly the four `PROVIDER_SURFACES` and closed-set values. An absent
   entry gives `release_registry_entry_fields_invalid`. A null, missing,
   extra or unknown value gives `release_registry_provider_dispositions_invalid`.
3. Each legacy entry declares what it effectively received before.

**Per-release decisions.** Each decision is backed by review evidence; none
relies on the old default alone. Evidence was gathered read-only from the
current source and history.

## 3. F-01 — F3 re-apply validates `expected_plan_hash`

**Defect.** `F3RuntimeIntegration._apply`, when a task already existed,
compared the stored task hash with the recomputed plan hash. It never compared
either with the caller's `expected_plan_hash`. A re-apply with an empty or
wrong hash could resume or replay an initialized task. The first apply
(`_initialize`) and the legacy path (`handle_legacy_apply`) both refuse that
case.

**Change.** After the existing storage-integrity check and before
`_load_prepared`, dispatch, task events or plan changes, the branch refuses
`not expected_plan_hash or expected_plan_hash != task.plan_hash` with
`approval_hash_mismatch`. That is the same predicate and error as the legacy
path. A matching same-ID replay is unchanged: a terminal task returns the same
task with no redispatch, and an undispatched initialized task resumes and
dispatches once.

## 4. F-02 — honest principal-separation reporting

**Defect.** Every Ingress decision stored `principal_separation_enforced: true`,
including decisions under the anonymous fallback principal
`home_assistant_admin_ingress`. `approval_web.py` uses that principal when
Home Assistant supplies no `X-Remote-User-Id`, and it does not prove a distinct
principal.

**Change (reporting only).**

- Writer (approve and reject): `principal_separation_proven(principal)` is
  `true` for an identified `home_assistant_admin_ingress:<id>` principal and
  `false` for the anonymous fallback.
- Projection: every public plan projection (`_public`: `get_change_plan`,
  creation results and the `plan` object in apply, rollback and task results)
  uses `principal_separation_status(approval)`. `list_change_plans` summaries
  carry no separation field:

  | Recorded state | `principal_separation_enforced` | `principal_separation_status.reason` |
  | --- | --- | --- |
  | No Ingress decision yet | `null` | `no_external_approver_exists` |
  | Identified principal | `true` | `external_administrator_distinct` |
  | Anonymous fallback (new record, stored `false`) | `false` | `anonymous_fallback_principal` |
  | Anonymous fallback, pre-HAMCP-184 record stored `true` | `false` (projected; record not rewritten) | `anonymous_fallback_principal` |

- Eligibility is unchanged. The apply gate previously required a truthy flag.
  It now requires `_external_principal_authority_valid`: either a stored
  `true`, or a stored `false` with the anonymous fallback principal on a
  `standard_admin` plan. That is exactly the set of decisions that were
  eligible before, because elevated plan approval already refuses the fallback
  with `approval_principal_mismatch` and prohibited plans cannot be approved.
  A forged `false` with an identified principal is refused.
- Persisted records are never rewritten. F3 approval-bundle hashes bind the
  stored flag (`f3_runtime/runtime.py`, `f3/operational_adapter.py`), and
  historical elevated records require `true`
  (`governance/historical_policy.py`), which is unaffected.

**Surfaces.**

- The plan record and every plan projection report the values above
  consistently.
- The task `approval_reference` and the audit records carry no separation
  claim. Audit carries only `approval_principal_present`. They therefore cannot
  contradict the plan. No audit or task schema change was made.

**How today's live approvals will display after upgrade.**

- Existing approved, consumed or rejected plans decided through the Ingress
  panel without a Home Assistant user identity were stored with
  `principal_separation_enforced: true`. They will now read
  `principal_separation_enforced: false`, with `principal_separation_status`
  `{evaluated: true, enforced: false, reason: anonymous_fallback_principal}`.
- Decisions recorded with an identified user keep `true` and
  `external_administrator_distinct`.
- Pending plans read `null` and `no_external_approver_exists`, as before.
- Apply eligibility of every existing record is unchanged.

## 5. F-06 — runner-rule drift

**Defect.** `ci.yml` job `exact-addon-runtime-acceptance` uses
`runs-on: ${{ matrix.runner || 'ubuntu-24.04' }}` from the
`prepare_exact_image_matrix.outputs.addon` matrix. The HAMCP-178 guard resolved
that expression to the declared `support_window.RUNNERS` constant, not to what
the generator actually emits. A generated row carrying an unpinned runner would
have passed.

**Change (no workflow edit).**

- `generated_runner_labels` resolves the reviewed `fromJSON` source to every
  `runner` value emitted by `scripts/support_window.py addon_matrix` for every
  tier in `TIERS`. The quoted literal fallback is resolved separately, as
  before.
- New assertions: the generated labels are non-empty, are a subset of
  `RUNNERS`, are pinned, and each row's runner equals `RUNNERS[architecture]`.
- Mutations: unpinned `RUNNERS` values, and a generator emitting
  `ubuntu-latest` while the constant stays pinned, both make the guard flag the
  real `ci.yml` job.
- `.github/workflows/AGENTS.md` states the rule: a matrix-supplied runner is
  allowed only through a reviewed `DYNAMIC_RUNNER_SOURCES` expression whose
  generated rows and literal fallback all resolve to explicit images.
