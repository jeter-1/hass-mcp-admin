# Engineering 2.2.0-beta.52 release notes

Beta 52 stages a production-path correction for literal label and finite
entity-set target scope. Engineering 2.2.0-beta.51 remains advertised until a
separately authorized protected promotion. Stable v1.1.2 and the 51-tool
Engineering catalog are unchanged.

## Selector-local complete evidence

Beta 51 could let a malformed but provably nonmember entity-registry record
make complete literal-label evidence globally incomplete. Two unrelated
monitoring sources consequently contributed 31 target-capable obligations and
two downstream profiles to a standard helper plan even though their complete
finite memberships excluded that helper.

Beta 52 binds completion per literal label selector. Exact Home Assistant label
ID lookup retains precedence over normalized display-name lookup, using the
reviewed Core normalization `name.casefold().replace(" ", "")`. Complete
membership is unioned with independently proven candidates and transported
through finite lists, mappings, branches, loops, reviewed filters, State
projections and bounded expansion. A complete set can now terminate as exact
inclusion or exclusion before downstream profiles, consequence, policy,
actionability, fingerprints and locks are aggregated.

Only evidence that is both bounded and internally sufficient becomes complete.
Malformed potential members, unreadable or excessive membership, duplicate
relevant identities, unavailable inventory, conflicting lookup evidence,
dynamic labels, caller-supplied selectors, imported/unknown contracts,
unbounded collections and coverage failure remain conservative. Exact
inclusion survives mixed incomplete provenance, and retained prefixes never
prove exclusion.

The sanitized Beta 51 replay reproduces the released 31-obligation/two-profile
failure through the actual provider and dependency index. The corrected
standard result is complete, low/`standard_admin` and actionable with zero
exact target dependencies, zero target-relevant opacity and zero downstream
profiles. Genuine consequential dependencies remain high/`elevated_admin` but
actionable; arbitrary selectors and coverage failures remain blocked.

New plans use `helper-dependency-risk-v11`. Persisted v3-v10 plans remain
readable with their historical hashes and classifications, but require a fresh
v11 plan and cannot authorize current approval or execution. Every plan binds
the exact dependency-index generation, fingerprint and source epoch it
consumed, including selector-local membership fingerprints and completion.

## Compatibility and release boundary

The exact helper lock and shared dynamic stability fence remain present on
executable helper operations. Exact downstream locks remain proportional;
excluded and neutral sources add no downstream lock, while genuine opacity and
coverage failure retain the unconstrained guard. Final-preflight drift remains
fail-closed before provider dispatch.

No Jinja rendering or execution, public MCP schema, tool registration, provider
admission or routing, fallback, write authority, approval authority, task
schema, workflow, container, deployment behavior or stable-v1 change is
introduced. HAMCP-089 is not accepted by source staging. Post-deployment
planning acceptance and any reversible helper canary require separate
authorization.
