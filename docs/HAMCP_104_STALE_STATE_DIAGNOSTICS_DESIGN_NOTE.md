## 3. Proposed change

**Slice A: precise category (vocabulary only).**

- Add to `_REASONS` with existing checks. `target_state`: `delete_target_missing`,
  `config_entry_missing`, `config_entry_not_loaded`, `entry_entities_changed`,
  `options_schema_changed`, `option_not_available`, `stale_dashboard_state`,
  `stale_baseline`, `dependency_risk_drift`. `plan_binding`:
  `current_state_binding_mismatch`. `provider_read`: `label_namespace_unavailable`.
  `provider_admission`: `dashboard_provider_identity_changed`,
  `dashboard_provider_contract_changed`.
- Split the dashboard code: `stale_dashboard_state` (config hash) versus
  `dashboard_provider_contract_changed` (version/protocol/compatibility/identity).
- Helper options: a domain change returns `resource_identity_mismatch`; `modified_at`
  keeps `stale_target_state`.
- Keep `_REASONS` priority so lock and plan-binding codes still win. Refusal
  decisions, counters and zero dispatch are unchanged.

**Slice B: bounded `stale_state` evidence.** Optional object in the reason,
`reason_schema_version` 2:

- `kind`, closed enum: `content_changed`, `target_missing`, `target_appeared`,
  `identity_changed`, `baseline_changed`, `dependency_changed`,
  `called_script_changed`, `namespace_changed`.
- `expected_fingerprint_prefix` / `observed_fingerprint_prefix`: 12 lowercase hex or
  `null`.
- `mismatch_fields` (closed vocabulary, e.g. `entity_state`, `backup_inventory`,
  `reload_domain`, `addon_identity`, `runtime_identity`; max 4) plus
  `mismatch_fields_truncated`.
- "Which target" is already in the reason: `operation_id`, `ordinal`, `target_type`,
  `target_id`.

Persistence (proposed): prefixed diagnostic codes `stale_fp_expected_<hex12>`,
`stale_fp_observed_<hex12>`, `stale_field_<name>`, `stale_fields_truncated`, following
the HAMCP-249 verifier-location precedent (`pre_dispatch_reasons.py:244-330`). They fit
`EVIDENCE_PATTERN` and the 16-item cap (`:20-21`); worst case is 9 items. The adapter
emits the primary code first because `bounded_diagnostics` slices before filtering
(`:24-31`). The decoder maps unknown names to `unrecognized_field` and never echoes
values.

Bounds: prefixes appear only where the adapter already computes both fingerprints
(configuration lanes, dashboard); otherwise `null`, never fabricated. No raw
configuration, state values, option strings or secrets are stored or returned. The
expected fingerprint is already public for configuration plans
(`E/governance/models.py:343`, `:452`). No change to routing, provider dispatch,
fallback, retry or approval consumption.

## 4. Public schema / tool-registration impact

No tool, input schema or route changes; no tool declares an `outputSchema`. The
envelope stays `success: true` / `failed_pre_dispatch`. Output changes: Slice A turns
about 12 `unclassified_pre_dispatch_refusal` cases into precise codes (additive
vocabulary); Slice B adds `stale_state` and `reason_schema_version: 2` inside
`pre_dispatch_refusal`. `recorded()` accepts versions 1 and 2; stored version-1 tasks
are never rewritten. Because the reason is persisted, Slice B's compatibility test
must read version-1 records produced by the exact shipped code (root `AGENTS.md`
"Persisted Compatibility Fixtures"). The implementation PR adds a stale-state section
to `ERROR_TAXONOMY.md`.

## 6. Negative reachability and refusal tests

1. Parametrize every Slice A code across the `:559` surface matrix: zero writes,
   `dispatch_intent is None`, approval consumption unchanged, precise `error_code`
   and `check`.
2. Dashboard hash-only change gives `stale_dashboard_state`; version or identity
   change gives `dashboard_provider_contract_changed`; both refuse with zero dispatch.
3. Helper options domain change gives `resource_identity_mismatch`; `modified_at`
   gives `stale_target_state`; neither dispatches.
4. Hostile values: secret-like config/state values and option text matching
   `EVIDENCE_PATTERN` never appear in the reason, log or audit.
5. Malformed fingerprint codes (wrong length, uppercase, unknown field name, over 16
   items) yield `null` or `unrecognized_field`, never a fabricated `kind`.
6. Lock and plan-binding codes still take priority over the new codes.
7. Version-1 records still read (keep `:166`). Downgrade: shipped `recorded()`
   rejects a version-2 or new-code reason and falls back to `unknown_legacy` without
   crashing.

## 7. Acceptance

- **Success:** every stale site in section 2 returns a stable precise `error_code`,
  `check` and `kind`; configuration and dashboard refusals carry 12-hex prefixes;
  operational refusals carry `mismatch_fields`.
- **Refusal:** every refusal still occurs before dispatch with zero attempts and the
  same task state and envelope.
- **Failure preservation:** restart recovery and the legacy no-mutation set
  (`E/governance/storage.py:1655-1665`) are unchanged; existing HAMCP-249 tests pass
  apart from the expected precise codes.
