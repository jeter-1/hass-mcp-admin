## Canonical duplicate rule

The provider applies the existing raw entity-record bound before any
deduplication. Every retained record must be a JSON mapping and must serialize
as complete deterministic canonical JSON: sorted mapping keys, compact
separators, UTF-8, strict JSON scalar types, preserved list order, no coercion,
no `default=str`, and no non-finite number. A 65,536-byte canonical-record
budget, 4,096-node budget and bounded depth are enforced before serialization;
oversized or wide records remain noncanonical and fail closed. Each provider
pass also caps aggregate retained canonical bytes at 16,777,216. Exhaustion
marks selector evidence incomplete with
`entity_registry_canonical_byte_bound_exceeded`; canonical bytes beyond the
budget are not retained. Raw record-count bounds still run first, and
oversized-response ordering retains only fixed-size canonical digests. Records
are grouped only by an exact validated `entity_id`.

Multiple records collapse only when every complete canonical JSON byte string
is identical. Accepted multiplicity changes diagnostic anomaly evidence but
does not change membership, membership or selector-authority fingerprints,
candidate sets, target outcomes, helper-risk evidence fingerprint,
actionability, preflight authority or F3 locks. Mapping-key order, including
nested mapping-key order, is immaterial; list order, `1` versus `1.0`, boolean
versus integer, labels and every unrelated field remain material.

Any differing record under the same ID is a conflict. The provider never
merges fields, unions authority, chooses a winner or repairs values. A conflict
invalidates every selector whose membership could be affected; a readable
unrelated label collection remains selector-local. An unreadable label
collection, relevant malformed or noncanonical record, unavailable inventory,
label conflict, membership overflow, raw overflow or selector overflow remains
incomplete and conservative.

## Selector-authority diagnostics and compatibility

Fresh bindings use `helper-dependency-risk-v12`. For every retained literal
label selector, the plan persists a bounded, hash-safe diagnostic record with
lookup mode, hashed selector/resolved-label identity, completeness and exact
failure codes, membership/candidate counts and fingerprints, target
disposition, inventory availability/completeness, raw and canonical counts,
duplicate/conflict/malformed counts, raw-bound status, and dependency snapshot
generation/fingerprint/source epoch. It stores no raw registry record,
endpoint, credential, raw configuration or unrelated entity identity.

The existing `get_change_plan` summary detail envelope paginates these records
with its existing cursor and page-size inputs. Historical plans with no such
records retain their prior summary path. Pagination reads persisted data only;
it does not refresh evidence, approve, lock or dispatch.

Persisted v3-v11 plans remain readable and hash-stable, but only v12 is current
execution authority. Historical plans remain non-actionable, require
replanning, and cannot acquire current execution authority. The Beta 52 plan
remains historical failed-closed evidence and is not reinterpreted or migrated.
